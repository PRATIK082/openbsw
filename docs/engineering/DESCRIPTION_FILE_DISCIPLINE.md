# Description-File Discipline — DBC / ARXML / LDF / FIBEX

**Status:** Policy + CI proposal (N5.4). No description files are currently stored in this repo
(search found none); this document defines how they must be managed once introduced.

## 1. Purpose

Establish a single source of truth for communication descriptions (CAN DBC, LIN LDF, Ethernet/
SOMEIP FIBEX/ARXML, AUTOSAR ARXML) and enforce integrity via hashing + CI checks, so generated
code and runtime configuration cannot drift from the agreed network design.

## 2. Scope

- Formats: DBC (CAN), LDF (LIN), FIBEX (FlexRay/Eth), ARXML (AUTOSAR Classic/Adaptive ECU
  extract), plus any OEM-specific XML/JSON.
- Consumers: `tools/can/dbc_to_openbsw.py` codegen, `commgateway`, `cpp2can`, `cpp2ethernet`,
  `cpp2someip`, `framegateway`, NM timing config.

## 3. Source-of-truth layout

Recommended repository layout (to be created):

```
descriptions/
  can/
    vehicle.dbc
  lin/
    vehicle.ldf
  eth/
    vehicle.fibex
  autosar/
    ecu_extract.arxml
  hashes/
    manifest.sha256
```

- One canonical file per bus/network; no duplicates.
- Generated artifacts (tables) go under `src/config/generated/` and are committed OR rebuilt in CI
  (choose one policy; recommend committed for reproducibility with hash check).

## 4. Hashing & manifest

- Compute SHA-256 for every description file.
- Store in `descriptions/hashes/manifest.sha256` with relative paths:
  ```
  <sha256>  can/vehicle.dbc
  <sha256>  lin/vehicle.ldf
  ```
- Regenerate manifest on any description change via `sha256sum` / `Get-FileHash`.
- Commit manifest in the same PR as the description change.

## 5. Codegen & regeneration

- `tools/can/dbc_to_openbsw.py` reads DBC → generates `*Tables.h`, `FrameConfig_table.cpp`,
  `SignalConfig_table.cpp`. Must be re-run when DBC hash changes.
- Equivalent generators for LDF/FIBEX/ARXML to be added (currently missing — tracked as gap).
- Generated files carry header comment `// Generated by ... from <file> -- DO NOT EDIT.` plus
  source file name and hash for traceability.

## 6. CI checks (proposed)

1. **Hash check:** Recompute SHA-256 of all files under `descriptions/` and compare to manifest;
   fail on mismatch or untracked description file.
2. **Freshness check:** Regenerate codegen outputs in CI and `git diff --exit-code` against
   committed generated files; fail on drift.
3. **Schema validation:** DBC parseable by `cantools`; LDF/ARXML well-formed XML; FIBEX schema.
4. **Naming/versioning:** Require description-file version bump (in filename or header) when content
   changes; changelog entry.
5. **Busload re-analysis:** Trigger `BUSLOAD_ANALYSIS.md` numbers update when hashes change
   (manual gate, not automated initially).

## 7. Review & change control

- Description-file changes require network/communication owner review.
- PR template: attach hash diff + regenerated table diff + busload impact.
- No hand-edits to generated tables; CI freshness check enforces.
